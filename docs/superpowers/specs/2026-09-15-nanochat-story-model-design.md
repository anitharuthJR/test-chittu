## 1. Goal and non-goals

**M1 delivers** a reproducible, Mac-only pipeline that trains a from-scratch
TinyStories-class story model with nanochat, from a corpus that Chittu's *own* L1 and
L6 guards have swept, and ends in a checkpoint you can chat with plus an honest
scorecard.

**M1 does not deliver** a model that serves children. That is M2+ — a GPU run, then the
gates in §2.3. Nothing in M1 touches the router, the pipeline, or any child-facing path.

## 2. Context and doctrine

### 2.1 Why from-scratch, and why only stories

The pause (`docs/chittu-status.md` §6b) stopped fine-tuning an open base because a
fine-tuned 4B model was "not good enough to be the open-ended voice" and G2 never held
across seeds. A from-scratch model on a curated corpus makes a different claim: it
cannot say what it never read. That claim is only credible where a tiny model is also
*useful*, and TinyStories (Eldan & Li, 2023) showed 1M–33M-parameter models writing
coherent children's stories. The architecture already anticipates exactly this cell:

- `docs/chittu-architecture.md` §12.2 — "Offline stories (Phase 2) — TinyStories-class
  SLM — coherent children's stories from tiny models; the on-device path".
- `docs/chittu-requirements.md` — the model table's creative row names a
  "TinyStories-class SLM for offline on-device stories", and the on-device SLM item
  repeats it.
- §12.4 Phase 3 — a generation cell is gated by a **free-generation quality eval, not
  the routing scorecard**.

### 2.2 What binds the data

- `docs/chittu-architecture.md` §11: never a child's turn; `training_origin` has no
  `CHILD_TURN`; `training_run` must carry `dataset_sha256`.
- TinyStories is synthetic, third-party text (Microsoft Research; GPT-3.5/GPT-4
  generated; licence CDLA-Sharing-1.0). In Chittu's enum that is `SYNTHETIC` —
  "generated by a model, human-reviewed". 2.7M stories cannot be read by a human. M1's
  honest substitute: a mechanical L1 + L6 sweep over every record, tag exclusion, and a
  *sampled* human read recorded in the sweep report. Whether that satisfies the enum's
  intent is an open question for a human (§12), not something this spec decides.

### 2.3 Gates before this model ever carries a child turn (M2+, listed so M1 cannot be mistaken for them)

1. Free-generation quality eval (§12.4 Phase 3).
2. Red-team corpus in every language the L1 lexicon covers (§12.5).
3. A `training_run` row with `dataset_sha256` and `g2_passed` (§11.4).
4. A routing decision — the router has no story category today (`classifier | sandbox |
   homework | curriculum | vision | embedding`); serving creative-mode `sandbox` calls
   from this model is its own decision.

Data, the uv environment and checkpoints live under `~/.cache/nanochat-chittu/` and
never enter the tree. Only two upstream files are modified, so `git subtree pull
--squash` stays cheap. nanochat's `.claude/skills/read-arxiv-paper` arrives as a
directory-scoped skill; it is harmless and left intact to avoid pull conflicts.

### 3.2 The subtree

```bash
brew install git                                    # Homebrew git ships contrib/subtree
git fetch https://github.com/karpathy/nanochat.git master
git subtree add --prefix=llm-kit/nanochat 92d63d4e8bb4df75c3b71618f31ddde2378b2bcd --squash
# later, deliberately:
git subtree pull --prefix=llm-kit/nanochat https://github.com/karpathy/nanochat.git master --squash
```

Pin `92d63d4` even if master has moved by implementation time — reproducibility of this
spec beats freshness; the README records the newer HEAD if there is one. The squash
commit's `git-subtree-split` trailer is the upstream provenance; `SOURCES.json` and every
MANIFEST repeat the SHA so it is answerable without git.

### 3.3 The two upstream patches

- **`nanochat/dataset.py`** — `DATA_DIR = os.environ.get("NANOCHAT_DATA_DIR") or
  os.path.join(base_dir, "base_data_climbmix")`. Reusing the upstream directory name
  would put TinyStories under a path called `base_data_climbmix` — a lie in a path.
  Consequence: `python -m nanochat.dataset` is **never run** in this tree; with the
  variable set it would pour ClimbMix shards into the story corpus. The README says so
  and the recipe never calls it.
- **`scripts/chat_sft.py`** — a `--mixture {default,chittu_stories}` argument. In the
  existing mixture block, the `chittu_stories` branch sets
  `train_tasks = [ChittuStories("train")]` and `val_dataset =
  TaskMixture([ChittuStories("val")])`, importing inside the branch. The `default` path is
  byte-for-byte unchanged.

### 3.4 Data flow

```
TinyStories_all_data.tar.gz ──verify sha256──▶ prepare_stories.py ──▶ stories.raw.jsonl
   (2.7M records: story, instruction{prompt,words,features}, summary, source)
stories.raw.jsonl ──▶ pnpm story:sweep (scan() + passesOutputFilter()) ──▶ stories.kept.jsonl + sweep report
stories.kept.jsonl ──▶ build_dataset.py ──▶ $NANOCHAT_DATA_DIR/shard_*.parquet (last = val)
                                        ──▶ stories.sft.{train,val}.jsonl
                                        ──▶ MANIFEST.json (dataset_sha256)
shards ──▶ tok_train (8192) ──▶ base_train (d6) ──▶ chat_sft (--mixture=chittu_stories)
        ──▶ story_eval.py ──▶ generations.jsonl ──▶ pnpm story:sweep --fields text ──▶ scorecard
```

### 4.1 `chittu/SOURCES.json`

```json
    }

```

The tarball's sha256 is the LFS object id HF serves as `x-linked-etag`, which is the
file's sha256; the prompts file is small (11,759 bytes, not LFS) and was hashed after
fetching. Exact byte counts are recorded in the MANIFEST after the first verified
download, never pinned by hand. A hash mismatch aborts.

### 4.2 `chittu/prepare_stories.py` — pin, verify, filter (pre-sweep)

- Downloads each source into `~/.cache/nanochat-chittu/sources/` if absent, with a
  `.tmp` then rename, and **verifies sha256 before reading a byte**; mismatch aborts.
- Streams the tar's `data*.json` members in archive order — fixed by the pinned sha256 —
  in one pass (`r|gz`; each member is a JSON array, loaded whole, ~30 MB).
- **Schema assertion** per record: `story: str`, `instruction.words: list`,
  `instruction.features: list`, `summary: str`, `source: str`. A missing field aborts
  naming member and index — no silent skipping. (Note the upstream quirk: the prompt
  key is literally `"prompt:"`; it is not used.)
- Filters, all reported: `--source GPT-4` (default; `any` keeps GPT-3.5 rows);
  `--drop-features BadEnding` (default; repeatable); exact-duplicate stories dropped by
  sha256 of the stripped story.
- Output, both under `$NANOCHAT_DATA_DIR`: `stories.raw.jsonl` —
  `{id, story, words, features, summary, source}` with `id = sha256(story.strip())[:16]`,
  stable across runs — and `prepare-report.json`: total, per-source, dropped-by-feature,
  duplicates, kept.
- `--limit N` stops after N kept records (smoke runs only). Every step of the data path
  (prepare, sweep, build) skips itself when its output already exists, unless
  `--force`: the one-time full preparation is cached, not repeated.

### 4.3 `pnpm story:sweep` — Chittu's own gate over the corpus

`apps/api/src/story-corpus/sweep.ts`:

```ts
export type Verdict =
  | { keep: true }
  | { keep: false; gate: 'L1'; kind: L1Kind }
  | { keep: false; gate: 'L6' };
export function judgeStory(text: string): Verdict;                             // scan() then passesOutputFilter()
export function joinFields(record: Record<string, unknown>, fields: readonly string[]): string; // named string fields, '\n'-joined
export function judgeRecord(record: Record<string, unknown>, fields: readonly string[]): Verdict; // judgeStory(joinFields(…))
export function emptyReport(fields: readonly string[]): Report;
export function tally(report: Report, id: string | null, verdict: Verdict, text: string): void; // counts + ≤10 samples per kind
export function renderReport(report: Report, title: string): string;           // the .md; human-read section blank
// stream.ts
export function sweepStream(input: Readable, output: Writable, fields: readonly string[]): Promise<Report>;
```

The CLI (`apps/api/scripts/story-sweep.ts`) owns argv and file handles only and calls
`sweepStream`; everything that decides is pure and unit-tested. `apps/api/scripts/` is
outside `tsconfig`'s `include`, which is one more reason no logic lives there.

- Imports `scan` and `passesOutputFilter` from `@chittu/safety-kernel` — the real guard,
  not a copy of its regexes. `scan` dispatches `crisis → pii → unsafe → secret → identity
  → profanity`; the verdict names the first that fired.
- Judges the named fields joined with `\n` — default `story,summary`, because the
  summary becomes prompt text the model sees; `--fields text` for generations.
- Streams line by line with an own `\n`-only splitter (`jsonlLines`, `StringDecoder`),
  not Node's `readline` — `readline` also breaks lines on U+2028/U+2029, which split a
  TinyStories record mid-text and aborted the sweep with `not JSON`; preserves order and
  records untouched.
- CLI: `pnpm story:sweep -- <in.jsonl> <out.jsonl> <report.json> [--fields a,b]`. Writes
  `report.json` and a rendered `report.md` beside it.
- Report: `total`, `kept`, `dropped` by gate and kind, up to 10 verbatim samples per kind
  (synthetic text — safe to keep), the field list, the kernel's `L1_ORDER`, and a
  **"Sampled human read"** section in the `.md` left blank for a person. A script must
  not fill in a human judgement.
- No threshold and no `--keep-kinds`. Every kind drops. Over-dropping costs data (2.7M
  sources); under-dropping costs a child. A surprising drop rate is a finding for the
  report, not a reason to loosen the gate.
- **L6 is not a subset of L1.** `BANNED_OUT` bans Chittu-voice attachment ("i love
  you", "i'll miss you", "i'm alive", "our little secret"), and TinyStories characters
  say "I love you, Mommy" constantly. Dropping those is deliberate: L6 runs on every
  sandbox reply at serve time, so a model that learned them would have its stories
  blocked on the way out and the child would get the scripted fallback. This is the first
  time L6 meets narrative dialogue at scale; the rate it drops is a number the Council
  should see, and the report carries it.

### 4.4 `chittu/build_dataset.py` — exactly what nanochat consumes (post-sweep)

- Seeded shuffle (seed 42). Validation = last 1 % of kept records, minimum 2,000,
  written as **exactly one** final shard whatever its size (nanochat's
  `parquets_iter_batched('val')` reads the last file).
- Training shards `shard_00000.parquet …` under `$NANOCHAT_DATA_DIR`: column `text`
  (the stripped story), 50,000 stories per shard, 1,000-row groups (nanochat iterates
  row groups).
- SFT pairs `stories.sft.train.jsonl` (cap `--sft-max 100000`) from training stories and
  `stories.sft.val.jsonl` (cap 2,000) from validation stories. Each line is
  `{"messages":[{"role":"user","content":P},{"role":"assistant","content":S}]}` with
  `S = story.strip()` and no system message. `P` is chosen deterministically by
  `int(id[:8], 16) % 100`:
  - `< 45` → words template: `Tell me a story using the words rescue, crown and quiet.`
    (comma-joined with a final "and"; fewer than three words joins what there is; no
    words falls through to the summary template);
  - `< 90` → summary template: `Tell me a story about this: <summary>`;
  - else → bare: `Tell me a story.` — so unconstrained requests are learned too.
- `MANIFEST.json`: source hashes, nanochat SHA, filters, counts at every stage, sha256 of
  every shard and SFT file, the sweep report's sha256, and `dataset_sha256` = sha256 of
  the newline-joined, sorted shard hashes — the value `training_run.dataset_sha256`
  will want. "What was this model trained on?" is answered from this one file.
- Writes `MANIFEST.json` into `$NANOCHAT_DATA_DIR`; the recipe copies it to
  `llm-kit/evals/story-d6-mac-<date>-manifest.json` so the card and its provenance are
  committed together.
- Asserts `--min-train` kept training stories, default 200,000 (the d6 run consumes
  ~250k; below that the run is a different experiment and should be re-planned, not
  silently shorter). Smoke runs pass `--min-train 1000`.

### 4.5 `tasks/chittu_stories.py`

`ChittuStories(Task)` on `tasks/smoltalk.py`'s pattern: loads the split's JSONL into a
list at init (~100 MB for 100k pairs), `num_examples`, `get_example` returns
`{"messages": …}` after the same role-alternation asserts SmolTalk performs. Reads
`$NANOCHAT_DATA_DIR/stories.sft.<split>.jsonl`.

### 4.6 `runs/chittu_story_mac.sh` — the recipe

Pasteable step by step, like `runs/runcpu.sh`. Environment:

| Variable | Value | Why |
|---|---|---|
| `NANOCHAT_BASE_DIR` | `~/.cache/nanochat-chittu` | keeps this track's cache apart from any stock nanochat cache |
| `NANOCHAT_DATA_DIR` | `$NANOCHAT_BASE_DIR/stories_data` | patch 1; honest path name |
| `NANOCHAT_DTYPE` | unset (fp32 on MPS) | nanochat's safe default; `bfloat16` is a knob, off — the "sharp edges" path |
| `SMOKE` | unset / `1` | `1` → the whole run is re-rooted under its own base dir `$NANOCHAT_BASE_DIR/smoke` (only the pinned source tarball is shared back in, via a `sources` symlink), so a smoke `tok_train` can never overwrite the real model's tokenizer: data in `smoke/stories_data` built from `prepare --limit 20000` and `build --min-train 1000`, 20M tokenizer chars, 50 pretrain iters, 20 SFT iters, `--eval-tokens=131072`, 3 + 3 eval probes, tag `story-d6-smoke`, card and sweep report under `smoke/cards/` (a smoke card is not an artefact and never lands in `llm-kit/evals/`). ~5 min once the 1.6 GB tarball is downloaded; the real run's directories are never touched |

Steps:

1. `uv sync --frozen --extra cpu --group dev` — uv fetches CPython 3.10
   (`.python-version`); torch 2.9.1's arm64 wheel includes MPS; `rustbpe` has arm64
   wheels, so no Rust toolchain; `dev` brings pytest. `--frozen` always: a bare `uv sync`
   rewrites `uv.lock`.
2. `uv run --frozen python -m pytest -q chittu` — pre-flight (`python -m` puts the tree
   on `sys.path`, so `chittu.*` and `nanochat.*` import without an install step).
3. `python -m chittu.prepare_stories`
4. `pnpm story:sweep -- $NANOCHAT_DATA_DIR/stories.raw.jsonl $NANOCHAT_DATA_DIR/stories.kept.jsonl llm-kit/evals/story-corpus-sweep-<date>.json` (run from the repo root; the recipe `cd`s for it).
5. `python -m chittu.build_dataset`
6. `python -m scripts.tok_train --vocab-size=8192 --max-chars=500000000` then
   `python -m scripts.tok_eval`.
7. `python -m scripts.base_train --depth=6 --head-dim=64 --window-pattern=L
   --max-seq-len=512 --device-batch-size=32 --total-batch-size=16384
   --num-iterations=5000 --eval-every=100 --eval-tokens=524288 --core-metric-every=-1
   --sample-every=100 --model-tag=story-d6-mac --run=dummy`
8. `python -m scripts.chat_sft --mixture=chittu_stories --model-tag=story-d6-mac
   --num-iterations=1500 --eval-every=200 --eval-tokens=524288 --chatcore-every=-1
   --run=dummy`
9. `python -m chittu.story_eval generate --model-tag=story-d6-mac --out-dir=$NANOCHAT_BASE_DIR/eval-story-d6-mac`,
   then `pnpm story:sweep -- <eval-dir>/generations.jsonl <eval-dir>/generations.kept.jsonl <eval-dir>/generations-sweep.json --fields text`,
   then `python -m chittu.story_eval card --out-dir=<eval-dir> --card=llm-kit/evals/story-d6-mac-<date>.md --manifest=$NANOCHAT_DATA_DIR/MANIFEST.json --timings=$NANOCHAT_BASE_DIR/timings-story-d6-mac.json`.
10. `python -m scripts.chat_cli -g story-d6-mac -p "Tell me a story about a brave little sparrow."`

Never in the recipe: `python -m nanochat.dataset`, `scripts.base_eval` (CORE), the
ChatCORE tasks. Each step records its wall clock into `$NANOCHAT_BASE_DIR/timings.json`
for the card. The one-time data preparation (download 1.6 GB, prepare, sweep, build) is
estimated at 15–30 min and is cached; the training and eval steps are the 1–2 h.
`<date>` is always `YYYY-MM-DD`.

### 4.7 Training configuration and the reasons

| Dial | Value | Reason |
|---|---|---|
| vocab | 8192 | a depth-6 model has ~10M transformer parameters; at 32k vocab the embedding tables outweigh the transformer. TinyStories reports ~10k active tokens. nanochat pads to a multiple of 64, so nothing else changes |
| depth / head-dim / window | 6 / 64 / `L` | `runs/runcpu.sh`'s shape exactly — the one configuration nanochat's author tuned for a Mac |
| seq len | 512 | a TinyStory is ~300 tokens at this vocab |
| batch | 32 × 512 = 16,384 tokens/step | runcpu's; fits 16 GB in fp32 with room |
| pretrain steps | 5,000 → 82M tokens ≈ 250k stories | under one epoch of the kept corpus |
| SFT steps | 1,500 → ~24M tokens ≈ 60k pairs | runcpu's; inside the 100k cap |
| CORE / ChatCORE | off | they measure general knowledge a kids-story model has no business having |
| wall clock | est. 1–2 h on this M2 Pro | runcpu is 30 + 10 min on an M3 Max with roughly twice the GPU; the measured time goes on the card |

## 5. Evaluation — `chittu/story_eval.py` and the scorecard

Two probes:

- **(a) completion** — the BASE checkpoint completes the paper's 44 evaluation prompts,
  200 tokens each, tokens = `[bos] + encode(prompt)`.
- **(b) requests** — the SFT checkpoint answers the 20 requests in
  `chittu/story_requests.txt`, written as a child types them ("tell me a story about a
  dog who wants to fly", "can you tell me a bedtime story") and never lifted from the
  SFT templates — the same rule as the crisis corpus. Tokens are built exactly as
  `scripts/chat_cli.py` builds them (`bos, user_start, …, user_end, assistant_start`).

Sampling is fixed and printed on the card: temperature 0.6, top-k 50, seed 42, ≤ 400
tokens, via `Engine.generate`.

Two sub-commands, because the hygiene numbers come from the TypeScript sweep in
between: `generate` writes `<eval-dir>/generations.jsonl` (`{probe, index, prompt, text}`;
not committed — the card holds every generation verbatim) and `<eval-dir>/eval-meta.json`;
`card` folds in the sweep report, the MANIFEST and the timings and writes the scorecard
`llm-kit/evals/story-d6-mac-<date>.md`:

1. **Config** — upstream SHA, depth, vocab, iterations, tokens seen, wall clock per stage,
   final `val_bpb`, `dataset_sha256`, sampling parameters.
2. **Generations** — all 64, verbatim.
3. **Generation hygiene** — produced by `pnpm story:sweep --fields text` over
   `generations.jsonl`: L1 hits by kind, L6 fails, and the two rates.
4. **Human read** — a rubric (coherent? vocabulary a 4-year-old knows? follows the
   request? reaches an ending?) left blank for a person.

Three numbers: `val_bpb`, L1-clean %, L6-clean %. A hygiene number under 100 % does not
fail M1 — M1's job is the pipeline — it is the first data point for M2's free-generation
gate, written down. **The card is the artefact; the summary line is a convenience.**

## 6. Testing

### 6.1 vitest — `apps/api/src/story-corpus/sweep.test.ts` (server project, in `pnpm test`)

Stories written as stories read, never from the patterns:

- **Positive control:** a benign story is KEPT. A sweep that drops nothing looks exactly
  like one reading the wrong field.
- One L1 drop per kind: a crisis line → `crisis`; a phone number → `pii`; a knife fight →
  `unsafe`; "don't tell your mum" → `secret`; a swear → `profanity`. (`identity` is
  covered if a natural story line trips it; otherwise the kind is documented as untested
  rather than forced with a pattern-derived phrase.)
- L6-only drop: a line L1 passes but L6 bans — candidate: a robot saying "I'm alive!";
  the candidate is confirmed against `scan()` at implementation. Plus the empty story.
- The summary is judged too: benign story + violent summary → dropped.
- Streaming: five lines in, order and ids preserved, `total = kept + dropped`, per-kind
  counts add up, samples capped at 10.

**Mutation checks (measured 2026-09-15):** dropping `scan` fails 9 tests; dropping
`passesOutputFilter` fails 4; judging only the first field fails 1; returning L6 for
everything fails 6 (the positive control among them). Kit: removing the schema
assertion fails 2; keeping duplicates fails 1; disabling `--min-train` fails 1; writing
validation first fails 2.

### 6.2 pytest — `llm-kit/nanochat/chittu/test_*.py` (`uv run --frozen python -m pytest -q chittu`)

Fixtures are tiny tarballs built in-test. Cases: schema assertion aborts on a missing
field naming member and index; GPT-3.5 rows and `BadEnding` rows dropped, duplicates
collapsed, `id` stable across two runs; SFT prompt rendering deterministic with the
45/45/10 mix and the no-words fall-through; shards carry column `text`, 1,000-row
groups, the last shard is validation and is one file; MANIFEST hashes identical across
two builds; `ChittuStories` yields alternating user/assistant and asserts on a malformed
line.

### 6.3 Upstream's own suite

`uv run --frozen python -m pytest -q -m "not slow" tests` inside `llm-kit/nanochat` once, on this Mac; the result
(pass / skip / fail per file, `test_optim` needs CUDA, `test_tasks` may need network)
recorded in `chittu/README.md`. It is not a gate — it is the baseline for "did our
patches break the thing we imported".

### 6.4 `pnpm verify`

## 13. Deviations recorded during implementation (2026-09-15)

Dated so a later reader can tell what M1 actually did from what this design said it
would do, without diffing the two.

- The decision landed as `docs/chittu-status.md` §6f, not §6d as §7's cross-references
  assumed — §6d and §6e already existed as sub-sections of §6c by the time this track
  opened.
- `--frozen` on every `uv sync` / `uv run` in the kit and in this spec, not only where
  originally written — a bare `uv sync` rewrites `uv.lock`, and a rewritten lock is a
  silent dependency drift the next person to run the recipe would inherit.
- The sweep (`apps/api/src/story-corpus/stream.ts`) streams with its own `\n`-only
  splitter (`jsonlLines`, backed by `StringDecoder`), not Node's `readline` as §6.1
  originally specified — `readline` also breaks lines on U+2028/U+2029, and four
  TinyStories records carry a bare U+2028 inside valid JSON text, which split a record
  mid-story and aborted the sweep with `not JSON`.
- The sweep CLI writes its kept file to `.tmp` and renames it only after both reports
  (`.json` and `.md`) succeed; `chittu/prepare_stories.py` does the same for
  `stories.raw.jsonl` — in both cases a partial file used to look complete to the
  caller's own skip-if-exists check.
- SFT pairs are capped at 1,600 characters (`build_dataset.py --sft-max-chars`) and the
  cap is proven with the real tokenizer, after `tok_train`, by `chittu/check_sft_fits.py`
  — not designed up front. nanochat's best-fit SFT packer never places a conversation
  longer than its `max_seq_len + 1`-token row; enough over-length pairs saturate its
  100-conversation buffer and the resulting all-padding row NaNs the masked loss. It
  happened at step 138, twice, before the cap existed.
- `SEQ_LEN` is one shell variable shared by `base_train --max-seq-len` and
  `check_sft_fits --max-seq-len`, not two independently-set values — the check only
  proves what `base_train` will actually enforce if both read the same number.
- SFT runs with `--load-optimizer=0 --warmup-ratio=0.1 --init-lr-frac=0.25`, not
  nanochat's defaults — the defaults restore the pretraining optimizer state and jump
  the LR from 5% to 80% of base with no warmup, and measured validation bpb rose 0.492 →
  0.563 in the first 100 steps under them.
- Both training stages (`base_train`, `chat_sft`) run under `caffeinate -i -s`, which
  prevents idle/system sleep only while the Mac is on AC power — not a general-purpose
  sleep guard. The real run's laptop slept on battery for 36 minutes mid-pretraining
  before this was added.
- The smoke run (`SMOKE=1`) is isolated under its own `NANOCHAT_BASE_DIR`
  (`$NANOCHAT_BASE_DIR/smoke`), not a shared base dir with a separate data directory as
  originally set up — nanochat writes the tokenizer to `$NANOCHAT_BASE_DIR/tokenizer`
  with no tag, so a smoke `tok_train` was overwriting the real run's tokenizer. Only the
  pinned source tarball is shared back into the smoke dir, via a symlink.
- `chittu/test_patches.py` pins `scripts/chat_sft.py`'s `--mixture` switch with a
  structural AST assertion, not only a text pin — a text pin cannot see indentation, and
  an upstream pull that un-indents the default-task branch out of the switch's `else`
  would instantiate SmolTalk/MMLU/GSM8K unconditionally while still matching a text grep.
- The real run's SFT stopped at step 1409, not the planned 1500 — nanochat ends SFT when
  its mixture's epoch is consumed rather than at a fixed step count. `story_eval
  generate`, the sweep over its generations, `story_eval card` and the `chat_cli` sparrow
  request all ran by hand afterward, since the recipe itself never reached the SFT stage
  that produces the checkpoint they need until the NaN fix landed.
- Mutation counts for the sweep and the kit are measured, not estimated, and recorded in
  §6.1 rather than left as a plan.
